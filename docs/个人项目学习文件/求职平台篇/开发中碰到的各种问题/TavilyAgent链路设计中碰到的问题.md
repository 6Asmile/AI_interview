## 统计已经说明根因不是模型单纯“思考慢”，而是三件事叠加：

- `tavily_search` 调了 13 次，Prompt 上限是 4；
- `tavily_extract` 调了 27 次，Prompt 上限是 3 个 URL；
- 其中 27 次 Tavily 调用失败并等待网络超时，错误都指向 `api.tavily.com → 198.18.0.95:443`；
- 第一个搜索子 Agent 失败后，主 Agent 又完整委派了第二次；
- 成功提取的正文又触发了 7 次大结果 `grep`，进一步增加模型轮次。

所以必须同时解决“网络快速失败、整任务超时、工具硬预算、禁止失败后整轮重试”。

## 实际耗时原因

我解析了全部 238 条 WebSocket 事件，统计结果是：

|项目|实际数量|原计划上限|
|---|---|---|
|网络研究子 Agent 委派|2 次|1 次|
|`tavily_search`|13 次|4 次|
|`tavily_extract`|27 次|最多读取 3 个 URL|
|搜索连接错误|10 次|应快速失败|
|正文提取连接错误|17 次|应快速失败|
|大结果 `grep`|7 次|未设置上限|
|最终状态|`cancelled`|应在有限时间内完成或失败|

因此，主要时间消耗在：

```
Tavily 网络连接超时
→ 模型看到错误后重试
→ 超过 Prompt 次数限制
→ 第一个子 Agent 失败
→ 主 Agent 再委派一个全新的子 Agent
→ 第二轮继续搜索和提取
→ 正文过大又触发多轮 grep
```

错误基本相同：

```
ClientConnectorError
api.tavily.com
198.18.0.95:443
TimeoutError(10060)
```

当前检查显示 TCP 443 又能连接，说明更像是本地代理/TUN/DNS 路径间歇性不稳定，而不是 Tavily 永久不可访问。但无论网络为何失败，Agent 都不应该因此循环十分钟。

另外还有两个行为问题：

- 模型主动把 `search_depth` 改成了 `advanced`，比我们的默认 `basic` 更慢；
- 同一份 Python 3.13 官方页面被反复提取了十多次。

这证明：

```
Prompt 里的上限只是建议，不是限制。
```
