# 网络研究失控与可靠性硬边界

## 问题现象

一次网络研究接近十分钟仍在继续搜索。更换网络后 Tavily 请求成功率提高，但 Agent 仍会重复调用工具，说明网络问题只是放大因素，主要问题是执行控制权过度交给模型。

## 根因

Prompt 中“最多搜索几次”属于软约束。模型可能：

- 忘记已经调用过几次；
- 使用近义查询重复搜索；
- 在并发工具调用中同时通过旧的预算检查；
- 让多个子执行分支分别认为自己还有预算；
- 工具失败后不断重试；
- 在已有足够证据后仍追求“更完整”。

## 方案比较

| 方案             | 能解决什么       | 不能解决什么          |
| -------------- | ----------- | --------------- |
| 只修改 Prompt     | 改善正常情况下的行为  | 无法提供执行保证        |
| 更换博查等供应商       | 可能改善网络和结果质量 | 无法阻止 Agent 重复调用 |
| 单个工具函数内计数      | 限制某个工具      | 难以统一委派、并发和跨工具预算 |
| Middleware 硬门禁 | 工具执行前统一拦截   | 仍需要任务级超时兜底      |
| 根任务总超时         | 保证最终结束      | 不能单独改善研究质量      |

最终采用三层方案：

```text
Prompt：告诉模型应该怎样做
Middleware / Budget：保证模型最多能做多少
Root Timeout：保证无论哪里阻塞都能够结束
```

## 已实现边界

- 一个根任务最多委派一次网络研究子 Agent；
- Tavily Search 根预算最多 4 次；
- Tavily Extract 根预算最多 2 次；
- 正文累计最多读取 3 个唯一 URL；
- 同一 AIMessage 最多并发两个搜索；
- URL 去掉 fragment、统一协议和域名大小写后再判重；
- Pydantic Schema 禁止模型添加搜索深度、结果数等额外参数；
- 使用 `ContextVar` 在一个根任务的异步子任务间共享预算；
- 不同 HTTP 根任务之间预算互相隔离；
- 供应商累计错误达到阈值后打开熔断器；
- 搜索和正文结果进入模型前均有单次与累计字符上限；
- 根任务总超时当前默认 150 秒；
- 超时后只产生一个 `failed` 终态、释放会话锁，不再产生 `completed`。

## 一个重要竞态

LangGraph ToolNode 可能用 `asyncio.gather` 并发执行同一 AIMessage 中的多个工具。如果只是普通的“检查计数 → await handler → 增加计数”，多个调用可能同时看到旧值并全部通过。

正确做法是在进入真实 handler 前同步完成预占或原子预算检查，被拒绝的调用不能访问供应商，也不能污染成功计数。

## 为什么换搜索供应商不是第一解决方案

更换供应商可以影响：

- 网络可用性；
- 搜索质量；
- API 延迟；
- 计费和配额。

但不能自动修复：

- 错误路由；
- 重复搜索；
- 无停止条件；
- 上下文膨胀；
- 最终模型超时。

因此先把供应商无关的执行边界做好，再比较 Tavily、博查等供应商才有意义。

## 验证

离线验证覆盖：

- 并发搜索预算；
- 被拒绝调用不进入 handler；
- URL 规范化和重复 URL；
- 搜索/正文内容字符预算；
- 静默供应商错误；
- 熔断后提前失败；
- 工具超时；
- 根任务超时和锁释放。

这些测试不调用 LLM、Tavily、MySQL 或 PostgreSQL，可以快速、稳定、低成本回归。

## 面试表达

> 我发现仅靠 Prompt 限制 Agent 搜索次数并不可靠，尤其在并发工具调用和网络错误场景下会出现预算穿透与重复重试。我将策略与执行约束分离：Pydantic 固化工具参数，Middleware 在 handler 前实施根任务共享预算、并发安全的 URL 去重和供应商熔断，再用 asyncio.timeout 约束整条任务链。最终用不依赖外部服务的离线测试覆盖并发、错误和超时，让 Agent 成本从“模型尽量遵守”变成后端可以保证的契约。
